# 06 — Схема даних протоколу

Як блок-схеми з [04](04-блок-схеми.md) записуються у машиночитаний граф. Реалізація читає цей граф; вона не містить клінічної логіки в коді. Зміна редакції протоколу — це нова версія графа, а не новий умовний оператор у клієнті.

Формат навмисно легкий: його має бути можливо валідувати офлайн на телефоні без рушія CQL чи DMN. Сумісність із FHIR `PlanDefinition` описана окремим мапінгом і **не реалізується в MVP**.

---

## 1. Модель вузла

Кожен вузол — одна дія або одне питання. Текст на екрані і голос збігаються дослівно з полями `voice.ua` / `voice.en`.

```json
{
  "id": "C2",
  "type": "action",
  "branch": "C",
    "roles": ["witness", "casualty"],
  "precedence": 5,
  "registry": ["A2", "A3", "A5"],
  "conflict": ["K6", "K7"],
  "veto": false,
  "handsBusy": true,
  "delegationRequired": true,
  "timers": [
    { "id": "pressure-hold", "startsOn": "confirm", "unit": "seconds" }
  ],
  "voice": {
    "ua": "Натисніть на рану обома руками. Тисніть сильно. Не відпускайте.",
    "en": "Press on the wound with both hands. Press hard. Do not let go."
  },
  "antiPattern": {
    "ua": "Не робіть джгут із ременя чи шарфа.",
    "en": "Do not make a tourniquet from a belt or a scarf."
  },
  "edges": [
    { "when": "yes", "to": "C3" },
    { "when": "cannot", "to": "C2-repeat" }
  ]
}
```

### Поля вузла

| Поле | Призначення |
| --- | --- |
| `id` | Стабільний ідентифікатор. Збігається з вузлом у [04](04-блок-схеми.md) (`A1`, `C2`, `D2`). |
| `type` | `question` — бінарне або 2–3 варіанти; `action` — наказ; `timer` — утримання дії; `report` — заповнення поля звіту; `handover` — експорт; `antipattern` — екран «не робіть». |
| `branch` | Літера гілки A–J. |
| `roles` | `witness`, `casualty`. Порожній масив заборонений валідатором, крім `type: antipattern`. Службових ролей немає. |
| `precedence` | Рівень драбини 1–10 з [03](03-пріоритети-та-конфлікти.md). |
| `registry` | Ідентифікатори записів [02](02-реєстр-протоколів.md) (`A2`, `B1`, `D`). |
| `conflict` | Ідентифікатори конфліктів `K1`–`K20`, якщо вузол їх розвʼязує. |
| `veto` | `true` — цей вузол зупиняє всі нижчі рівні (безпека сцени). |
| `handsBusy` | `true` — дія займає руки довше ніж хвилину. Валідатор вимагає ребро на вузол делегування. |
| `delegationRequired` | Повʼязане з `handsBusy`. |
| `timers` | Локальні таймери: утримання тиску, 5 хв до другої дози адреналіну, 24/48 год другої хвилі. |
| `voice` | Обовʼязкові `ua` і `en`. Текст = голос. Джерело істини для формулювань — [07](07-голосові-скрипти-UA-EN.md). |
| `antiPattern` | Необовʼязкове застереження, яке читається одразу після наказу. |
| `edges` | Переходи. `when`: `yes`, `no`, `cannot`, `next`, `timeout`, або ідентифікатор варіанта. |

Заборонені поля на вузлі: будь-які ідентифікатори постраждалого, діагноз, слово «dead».

## 2. Модель графа

```json
{
  "schemaVersion": "1.0.0",
  "protocolGraphId": "zero-echelon-core",
  "locale": ["uk", "en"],
  "commercial": false,
  "generatedFrom": {
    "precedence": "docs/03-пріоритети-та-конфлікти.md",
    "flow": "docs/04-блок-схеми.md",
    "registryChecked": "2026-09-13"
  },
  "entry": "Start",
  "alwaysAvailable": ["CALL-103", "CALL-101"],
  "nodes": [],
  "invariants": [
    "call-always-visible",
    "no-diagnosis",
    "no-dead-word",
    "no-reassurance",
    "no-vitals-counting",
    "source-required"
  ]
}
```

`alwaysAvailable` — вузли, досяжні з будь-якого стану. Це реалізація інваріанту 1 з документа 03: кнопка 103 ніколи не блокується.

`commercial: false` — інваріант ліцензії MC-IITT. Зміна на `true` має ламати збірку, доки запис A7 не вилучено або не замінено.

## 3. Правила валідації графа

Валідатор проганяється до збірки клієнта. Будь-яке порушення — помилка, не попередження.

1. Кожен вузол, крім `antipattern`, має непорожній `registry`.
2. Кожен вузол має `voice.ua` і `voice.en`; рядки збігаються з [07](07-голосові-скрипти-UA-EN.md) за `id`.
3. Немає недосяжних вузлів від `entry`, окрім `alwaysAvailable`.
4. Єдині дозволені цикли — повторна перевірка сцени (гілка A) і повтор чек-листа другої хвилі (гілка I). Інші цикли заборонені.
5. Вузол із `handsBusy: true` має ребро на вузол делегування або на вузол утримання до приїзду бригади.
6. Вузол із `veto: true` не має ребер у медичні гілки C–F; дозволені лише відхід, виклик і звіт.
7. Жоден `voice.*` не містить заборонених лексем: «мертв», «dead», «діагноз», «все гаразд», «можна не», «промийте шлунок», «викликайте блювання», «закрийте плівк», «джгут із ременя».
8. Немає вузла, який вимагає числа, підрахунку за секунди або показів приладу — крім метронома CPR і таймера турнікета, які продукт задає сам.
9. Поля звіту `M` і друге `E` не мають ребер від користувача; вони позначаються `filledBy: "service"`.

## 4. Журнал події (офлайн-лог)

Окремий обʼєкт, не частина графа. Пишеться локально, не синхронізується.

```json
{
  "eventId": "local-uuid",
  "startedAt": "2026-09-13T12:04:11+03:00",
  "location": {
    "level": 1,
    "qrId": "entrance-12-stair-3",
    "label": "Київська обл., м. Бровари, вул. …, підʼїзд 3",
    "gnss": null
  },
  "incidentType": "explosion",
    "role": "witness",
  "casualties": [
    {
      "localLabel": "Постраждалий 1",
      "color": "red",
      "notes": ["massive-bleeding", "pressure-held"],
      "tourniquetOn": "2026-09-13T12:06:40+03:00",
      "unreachable": false
    }
  ],
  "methane": {},
  "steps": [
    { "nodeId": "C2", "at": "2026-09-13T12:05:02+03:00", "edge": "yes" }
  ],
  "integrity": {
    "algo": "sha256-chain",
    "head": "…"
  }
}
```

Правила журналу:

- Постраждалий = ефемерний ярлик. Заборонені поля: ПІБ, дата народження, РНОКПП, адреса проживання, фото обличчя, геолокація точніша за адресу події.
- Кожен крок дописується хеш-ланцюгом: `hash(prevHash + canonicalJson(step))`.
- Автовидалення через 24 години після закриття події або одразу після підтвердженої передачі.
- Видавець ніколи не отримує копію.

Повна специфікація полів звіту — [08](08-звіт-M-ETHANE-та-передача.md).

## 5. Мапінг на FHIR (не реалізується в MVP)

Граф відповідає ідеї HL7 CPG-on-FHIR, але **не є** `PlanDefinition`. Причина: CQL і вкладені `PlanDefinition.action` потребують рушія, непридатного для офлайн-телефона в паніці.

| Наш елемент | Найближчий FHIR | Обмеження |
| --- | --- | --- |
| Граф | `PlanDefinition` type `clinical-protocol` | Лише експорт для майбутньої МІС-партнерки |
| Вузол-наказ | `ActivityDefinition` | Без кодів SNOMED у MVP |
| Вузол-питання | `Questionnaire` item | Лише так/ні |
| Журнал події | `CarePlan` + `Procedure` + `Observation` | Пише лише медпрацівник під КЕП |
| Неідентифікований постраждалий | `preperson` (власний API НСЗУ, не conformant FHIR) | Лише працівник стаціонару, п. 3.7.2 |
| Час турнікета | `Procedure.performedDateTime` | Переносить людина, не API |

Планувати «віддамо FHIR Bundle у ЦК ЕСОЗ» не можна: API НСЗУ — власний REST/JSON із вимогою КЕП, не сервер FHIR. Див. [10](10-право-регуляторика-ліцензії.md).

## 6. Версіонування і міграція

- `schemaVersion` — версія **формату** (поля вузла). Зміна назад несумісна.
- `protocolGraphId` + окремий файл версії графа (`zero-echelon-core@2026-09-13`) — версія **змісту**.
- Кожна зміна змісту проходить ланцюг: реєстр → документ 03 → документ 04 → цей файл → документ 07.
- Запланована міграція змісту: INSARAG, до 01.01.2027.
- Клієнт, відкритий офлайн, виконує граф тієї версії, яка закешована. Оновлення графа — лише при наявності мережі і лише цілим пакетом, з перевіркою підпису видавця.

Процедура зміни одного вузла: не редагувати JSON вручну в клієнті; змінити джерело в документах 02–04 і 07, згенерувати нову версію графа, прогнати валідатор.
